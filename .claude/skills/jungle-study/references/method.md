# 정글형 공부의 근거

SKILL.md의 동작이 어디서 왔는지 정리한 문서다. 동작 규칙이 애매할 때 "이 규칙이 지키려는 게 뭐였지?"를 확인하려고 읽는다. 사용자에게 이론 이름을 늘어놓으려는 문서가 아니다.

## 1. 야생 학습 (김창준, 『함께 자라기: 애자일로 가는 길』, 2018)

학교 학습과 달리 현업의 배움은 대부분 이렇다.

- 순서가 정해져 있지 않다(비순차적).
- 자료에 한정이 없다.
- 명확한 평가나 정답이 없다.
- 목표가 불분명하고 중간에 바뀐다.
- 혼자보다 함께 배운다(협력적).

이런 환경에서 잘 배우는 조건으로 책이 꼽는 것과, 스킬에서 맡은 동작은 다음과 같다.

| 책의 조건 | 스킬의 동작 |
|---|---|
| 실력과 난이도의 균형(몰입). 너무 어려우면 불안, 너무 쉬우면 지루 | '단계 이동'의 난이도 조절. 막히면 더 작게, 쉬우면 건너뛰기 |
| 불안할 땐 가장 간단한 프로토타입부터 | 1단계 '최소 사용법': 돌려 볼 수 있는 가장 작은 예시 |
| 짧은 주기의 구체적 피드백 | 원할 때 퀴즈, 풀어서 보내면 바로 채점. 실습 결과도 바로 피드백 |
| 기존 지식에 새 지식을 연결 | `_profile.md`를 읽고 아는 개념에 걸어 설명. Java/Spring 대응 개념 잇기 |
| 외부 지식을 재빨리 자기화 | 사용자가 보여 준 자기 프로젝트 코드를 첫 장면으로 쓰기, 실전 장면(코드 리뷰·에러 로그·장애) 먼저 보여 주기 |
| 튜토리얼을 읽으면서 "뭘 만들지" 정하기 | 단계마다 해 볼 실습 한 줄 제안, 원하면 손을 쓰는 실습 안내 |
| 회고와 자기 개선, 기록하고 나중에 확인 | 노트, 이어하기, 복습 |
| 지루할 땐 일부러 제약을 추가 | 이미 아는 주제면 난이도를 올린 실습(도구 없이, 테스트 먼저 등) |

## 2. Whole Game (David Perkins, 『Making Learning Whole』, 2009)

학교 교육은 야구 시합은 한 번도 안 하고 타격 연습만 시키는 꼴이라는 비판이다. 요소부터 다 배우고 나중에 합치는 대신, **작게 줄인 전체 게임(주니어 버전)을 먼저 해 보게 한다.** 그다음 어려운 부분만 따로 연습한다.

fast.ai(Jeremy Howard)의 실용 딥러닝 강의가 이 방식으로 유명하다. 첫 시간에 이미지 분류기부터 돌리게 하고, 층을 하나씩 벗겨 이론으로 내려간다. 그때쯤이면 학생은 모델을 더 잘 만들려고 이론을 스스로 원한다.

스킬에서는 이렇게 쓴다.
- 1단계는 "주니어 버전 게임"이다. 정의 대신 문제 → 장면 → 돌아가는 최소 코드.
- 넓은 주제는 통째로 다루지 않고 가장 먼저 부딪히는 한 조각으로 좁힌다.
- 3단계에서야 이론이 들어온다. 이론을 원하게 된 뒤에.

## 3. Just-in-time learning

필요할 때 필요한 만큼 배운다. 문제가 학습 범위를 정해 주니 방향이 분명하고, 배운 게 붙을 닻이 생긴다.

다만 **왜 됐는지 모르고 문제만 풀고 넘어가면 배운 게 아니라 운**이라는 경고가 같이 붙는다. 그래서 스킬은 1단계에서 넘어간 것을 '일단 넘어가는 것'으로 꼭 적어 두고, 3단계에서 갚게 한다. 실전 먼저, 기초는 버리는 게 아니라 나중에 한다는 사용자 요구와 정확히 맞는 지점이다.

## 4. Ultralearning (Scott Young, 2019)

9가지 원칙 중 스킬에 들어온 것은 다음과 같다.

- **메타러닝(지도 먼저 그리기)**: 배우기 전에 이 주제의 전체 지도를 본다. → 1단계 '주변 지도'
- **직접성(Directness)**: 실제로 쓰일 맥락에서 연습한다. → 상황 잡기, 사용자 코드 활용, 실전형 실습
- **드릴**: 약한 부분만 떼어 집중 연습한 뒤 다시 실전으로(direct → drill → direct). → 퀴즈에서 틀린 부분만 다시 설명하고 다시 묻기
- **인출(Retrieval)**: 다시 읽기보다 스스로 떠올리기가 훨씬 오래 남는다. → 퀴즈에 답을 같이 쓰지 않는 이유. 노트에 복습 문제를 쌓아 두는 이유
- **피드백**: 칭찬이나 비판 자체보다, 어떤 피드백을 어떻게 소화하느냐가 중요하다. → "어디까지 맞았는지 + 힌트 한 번" 방식

## 5. 튜토리얼 지옥과 Learn in Public

튜토리얼을 따라 할 때는 알아보기(recognition)만 쓰고, 혼자 시작할 때 필요한 떠올리기(recall)는 쓰지 않는다. 그래서 따라 할 땐 다 아는 것 같은데 빈 화면 앞에선 막힌다. 해결책은 직접 만드는 것이다. 실습이 "따라 치기"가 아니라 "직접 짜기, 일부러 깨뜨리기"인 이유다.

swyx의 Learn in Public은 배운 걸 공개적으로 남기라고 권한다. 남에게 설명하려고 정리하면 더 깊이 배운다. 노트는 그 작은 버전이다. 나중의 나에게 설명하는 기록이다.

## 6. 사용자 피드백에서 온 규칙

- **용어 먼저** (2026-10-31): 개발자라도 그 주제를 안 다뤄 봤으면 모르는 말이 있다. 그런 말이 설명 중에 갑자기 나오면 문장 전체가 막힌다. 단계 앞에서 짧게 풀어 주고, 너무 기초적인 개발 용어는 뺀다. 개념 자체의 교과서식 정의를 앞에 두라는 뜻은 아니다. 주제는 여전히 문제부터 들어간다.
- **버전 기준** (2026-10-31): 이 스킬은 프로젝트와 상관없는 폴더에서 쓴다. 작업 폴더의 프로젝트 버전에 맞추지 말고, 현업 안정 버전(Spring Boot 3.x 이상)으로 설명한다.
- **용어 기준 보강** (2026-10-31): HTTP 캐시 3단계에서 정작 사용자가 몰랐던 `ETag`가 풀리지 않았다. `validator` 풀이 안에 "(버전 지문)"으로 끼워 넣어졌고, 본문은 "ETag 만드는 법"부터 시작했다. 원인은 넷이었다. '헤더'가 기초 목록에 있었고, 하위 주제를 '주제 자체'로 보고 뺐고, 노트에 이름만 있던 걸 설명한 걸로 쳤고, 6개 상한에 맞추려 했다. 그래서 구체적인 헤더·옵션 이름도 후보로 넣고, 이름만 나온 건 설명한 게 아니라고 정했다. 애매하면 넣고, 다 쓴 뒤 한 번 훑는다.
- **비유는 아껴 쓴다** (2026-10-31): "쉽게 설명해"에 비유를 잔뜩 넣으면 근본 의미를 이해하기가 오히려 어려워진다. 원래 용어를 그대로 쓰는 편이 나을 때도 있다. 개발자에겐 실제 값, 코드, 요청·응답 예시가 먼저다. 비유는 한 개념에 하나만 쓰고, 쓰면 바로 실제 동작을 붙인다. "버전 지문"처럼 줄여 만든 말로 푸는 것도 같은 문제다. 사용자는 그 말이 무슨 뜻인지 몰라 ETag 풀이를 봐도 이해하지 못했다. 반대로 `Last-Modified`처럼 이름이 뜻을 말해 주는 건 따로 안 풀어도 괜찮았다.
- **실습과 퀴즈는 고르게** (2026-10-31): 직접 해 보면 더 깊이 남지만, 머리로만 이해하고 넘어가고 싶을 때도 있다. 그래서 기본은 설명 + 실습 한 줄 제안이다. 퀴즈는 원할 때만 내고, 형식(객관식·빈칸·OX·주관식)은 내용에 맞춰 고른다. 답은 가리고 채점한다. 대신 노트에는 복습 문제를 답과 함께 쌓아 둔다. 사용자가 퀴즈를 건너뛰어도 나중에 '복습하자'로 떠올려 보는 연습을 할 수 있다.
